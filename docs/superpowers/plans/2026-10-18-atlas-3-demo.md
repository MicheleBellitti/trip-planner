# Atlas step 3: the demo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A public, self-playing demo run at `/demo` that replays the recorded `happy-path` session through the real live components and ends in the real finished plan. It never calls the backend. The landing's "Guarda una corsa" points to it.

**Architecture:**
- `PlanScreen` splits into a presentational `PlanScreenView` and two data sources: `PlanScreen` (live, unchanged) and `DemoPlanScreen` (replay).
- `useReplayEvents` feeds the same `planEventsReducer` on a compressed schedule with a virtual clock.
- The demo route imports only demo modules, the fixtures and the shared view. `@/lib/api` is never evaluated in its graph.

**Tech Stack:** Next.js 16.4 App Router (Cache Components), React 19.3, Tailwind 4, Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-10-14-atlas-brand-design.md`, sections "Demo (`/demo`)" (§2) and "Delivery order" (§8, step 3).

**Michele's decisions (2026-10-17, from a mockup on a real demo run):**
- The recorded cost is shown, labelled as the cost of the recorded run, and the demo caption says it is free for the visitor.
- The run starts by itself on arrival.
- Autonomy through the PR.

## Global Constraints

- UI copy is Italian, sentence case. Code, comments and identifiers are English.
- No AI chrome (`components/ui/invariants.test.ts`).
- The tokens in `web/DESIGN.md` are the authority.
- Every page path comes from `ROUTES` or `lib/page-paths.ts`.
- Booking links stay the real, allowlisted links (CLAUDE.md contract rule 4). A booking keeps its two labelled dates (`DatePair`).
- `PlanScreen` keeps its signature `({ planId, client })`, and `components/live/plan-screen.test.tsx` stays green with its assertions unchanged.
- `/plans/[id]` first-load JS must not grow (192.8 KB gzip). Demo-only code lives in modules the plan page never imports (Turbopack keeps every export of a loaded module).
- No `Date.now()` or `new Date()` as the initial value of `useState`, `useRef` or `useMemo` (Cache Components prerender, invariant).
- Look at every screen at 393 px and desktop, dark and light. A screen merges at ≥ 32/40 in the impeccable critique with no open P0/P1.

## Review Focus

1. **The demo never reaches the backend.** It does not evaluate `@/lib/api` or `live-api`, open an `EventSource`, or `fetch` the API. That holds across the whole run, "Salta al piano", "Ricomincia" and the finished plan, including the trip's due dates and the cover. Test: Task 4.
2. **"Ricomincia" after the run, or mid-run, and "2×" toggled mid-run.** The run restarts from zero with live announcements working, and the speed change rescales only what is left, so the clock never jumps backwards. Test: Task 2 and Task 4.
3. **A visitor who leaves the tab in the background, or has reduced motion.** The replay still reaches the finished plan, and the clock shows replay time, never wall-clock drift. Test: Task 2.
4. **The live plan page is unchanged:**
   - same behaviour and tests;
   - its first-load JS does not grow;
   - its tab title still follows the plan.
   Test: Task 1 and Task 6.
5. **The demo's story is consistent.** The header summary, the coordinator's first message, the plan's "sotto il budget" and the cost line agree: 2 children aged 9 and 6, 2.800 €, the recorded 0,41 $. Test: Task 4.

### Task 2: `useReplayEvents`

**Files:**
- Create: `lib/demo/use-replay-events.ts`, `lib/demo/schedule.ts`
- Test: `lib/demo/schedule.test.ts`, `lib/demo/use-replay-events.test.ts`

**Interfaces:**
- `replaySchedule(events: UIEvent[], { target = 45_000, min = 80, max = 2_500 } = {}): number[]`
  - Returns one offset in ms per event from the replay's start.
  - Each recorded gap is clamped to [min, max] and the whole is scaled so the last offset is `target`.
- `useReplayEvents(events: UIEvent[], { speed: 1 | 2, epoch: string }): { state: PlanLiveState; now: number; done: boolean; skip(): void }`
  - Starts 600 ms after mount (`SETTLE_MS`) with a synthesized running snapshot: status `running`, `created_at` and `updated_at` = `epoch`, cost 0, `budget_cents` 60.
  - Dispatches each event re-stamped to `epoch + offset` when replay time reaches it. Replay time advances by real elapsed time × `speed`, measured with `performance.now()` deltas in an rAF or timeout loop.
  - Finishes with `end: ready`.
  - `now` is `epoch + replay time`.

- [ ] **Step 1: Failing tests.**
  - `replaySchedule`:
    - offsets are monotonic;
    - the first is 0 and the last equals `target`;
    - a recorded 5.5 s silence weighs no more than a clamped 2.5 s gap before scaling.
  - `useReplayEvents` with fake timers:
    - the status is `running` after `SETTLE_MS` and before the first event;
    - all 120 events land and the status ends `ready` after `target`;
    - `now` advances with replay time;
    - `skip()` lands every event and `end` at once;
    - `speed` 2 halves the time left from the moment it changes, and `now` never decreases;
    - with timers frozen (a background tab) and then resumed, the replay continues where it was and still ends `ready`.
- [ ] **Step 2: Run.** Expected: FAIL.
- [ ] **Step 3: Implement.** Use the pure schedule and a hook with its own `useReducer(planEventsReducer, undefined, initialPlanLiveState)`. The hook does not import `use-plan-events.ts` or `@/lib/api`.
- [ ] **Step 4: Run** `npx vitest run lib/demo`. Expected: PASS.
- [ ] **Step 5: Commit** `feat(web): useReplayEvents replays a recorded run on a compressed clock`.
